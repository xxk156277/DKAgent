目前成熟的开源 Agent Trace 设计，可以概括为：

以 OpenTelemetry 为骨架，以 typed span 表达 Agent 语义，以 Session/Trace 管理运行边界，以 Span Link 补充异步和多 Agent 因果关系，以对象存储承载大内容，以 Evaluation 作为独立实体，最终通过 OLAP/SQL 支撑查询、成本分析和质量评测。

不同方案的核心优势大致是：

Langfuse：高吞吐、产品级 Trace、成本和用户分析；
Phoenix/OpenInference：语义规范、RAG 调试、Annotation 和 Evaluation；
MLflow：Trace 与实验、数据集、反馈打通；
OpenLLMetry：自动埋点和后端无关；
OpenTelemetry GenAI：未来标准方向，但 Agent 语义仍需保留适配层。
真正值得直接复用的不是某个项目的完整表结构，而是这五个设计原则：

Trace 是一次 Run，Session 才是多轮会话。
Agent 行为必须拆成有类型的 Span，而不是一条大日志。
父子树之外必须支持 Span Link 和业务 correlation ID。
Trace 元数据与 Prompt 等大内容分开存储。
底层兼容 OTel，内部保留版本化 Canonical Schema。
Agent Trace 设计续集：成熟开源方案的生产级实现
截至 2026 年 8 月，开源 Agent Trace 已经出现比较清晰的收敛方向：

OpenTelemetry 负责 Trace ID、Span 树、上下文传播和 OTLP 传输；OpenTelemetry GenAI 或 OpenInference 负责 Agent/LLM 语义；Langfuse、Phoenix、MLflow 等在其上增加内容展示、评测、数据集和分析能力。

主流结构基本都是：

Session / Conversation
  └── Trace / Agent Run
        └── Span / Observation
              ├── Event
              ├── Link
              └── Content Reference

Assessment / Score  ──> Trace、Span 或 Session
OpenTelemetry GenAI 已经定义了 invoke_workflow、invoke_agent、plan、execute_tool 等 Agent 操作；Phoenix/OpenInference、MLflow、Langfuse 则补充了 LLM、AGENT、TOOL、RETRIEVER、GUARDRAIL 等更丰富的 Span 类型。

二、成熟系统真正记录的不是日志，而是“执行因果图”
一个合理的 Agent Trace 应该长这样：

纯文本
￼
￼
Session: conversation-9821

Trace: turn-18
└── WORKFLOW: answer-user-request
    └── AGENT: research-agent
        ├── PLAN: decompose-task
        ├── LLM: decide-next-action
        ├── TOOL: web-search
        │   ├── event: request.sent
        │   └── event: response.received
        ├── RETRIEVER: select-documents
        ├── LLM: synthesize-answer
        └── GUARDRAIL: output-check
这里有三个容易混淆的概念。

1. Session 不是 Trace
推荐：

纯文本
￼
￼
Session = 一段多轮会话
Trace   = 一轮用户请求，或者一个独立任务
例如用户连续发送 10 条消息：

纯文本
￼
￼
Session
├── Trace: turn-1
├── Trace: turn-2
├── Trace: turn-3
...
└── Trace: turn-10
不要把整个会话做成一个持续数小时甚至数天的 Trace。否则会产生：

Trace 永远无法结束
Span 数量持续增长
尾采样无法判断
查询和展示困难
单轮耗时与成本无法计算
异常归因困难
Langfuse 明确建议一个 Trace 表示一个自包含工作单元，再使用 Session 对多条 Trace 分组；OpenAI Agents SDK 也通过 group_id 关联同一会话中的多条 Trace。
￼￼
Langfuse
+2

2. Span 表示“有持续时间的操作”
例如：

纯文本
￼
￼
模型调用       → Span
工具调用       → Span
Agent 执行     → Span
向量检索       → Span
Guardrail 检查 → Span
Span 至少需要：

纯文本
￼
￼
start_time
end_time
status
parent_span_id
operation
input
output
error
3. Event 表示“瞬时发生的事情”
例如：

纯文本
￼
￼
stream.first_chunk
retry.started
rate_limit.received
tool.approval_requested
tool.approval_granted
checkpoint.saved
fallback.triggered
OpenTelemetry 的原则是：描述整个操作的稳定信息适合放 Span attribute；可能发生零次或多次、并需要独立时间戳的信息更适合放 Event。
￼￼
OpenTelemetry

三、推荐的 Agent Span 类型体系
不建议让业务方随意写：

纯文本
￼
￼
span.type = "some_action"
span.type = "do_something"
span.type = "step_1"
建议维护有限枚举：

Span Kind	含义
WORKFLOW	图、编排器或完整任务
AGENT	一个 Agent 的执行范围
PLAN	规划、任务拆分、路由决策
LLM	模型调用
TOOL	函数、API、MCP、Shell 等外部动作
RETRIEVER	数据库、搜索或向量检索
RERANKER	检索结果重排
MEMORY	长短期记忆读写
GUARDRAIL	输入、输出、安全或权限检查
HANDOFF	Agent 之间移交
EVALUATOR	在线或离线评测
CUSTOM	无法归类的自定义步骤
￼
￼
其中：

WORKFLOW/AGENT/PLAN/TOOL 可以映射到 OTel GenAI operation。
LLM/RETRIEVER/RERANKER/GUARDRAIL 可以参考 OpenInference。
MEMORY 可以参考 MLflow。
HANDOFF 可以参考 OpenAI Agents SDK。
