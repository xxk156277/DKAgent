
你是一名资深软件架构师、代码审计专家和技术导师。请对当前代码仓库进行一次“证据驱动的项目架构总结”

1. 项目解决什么问题
2. 系统由哪些部分组成
3. 核心业务如何运行
4. 数据如何流动
5. 
不要只根据 README 或文件名总结。必须阅读实际源码、配置、测试和入口文件后再下结论。

## 一、基本原则

- 先检查仓库，再输出报告。
- 优先分析真实执行路径，不要平均介绍所有目录。
- 明确区分：
  - 【事实】：源码或配置直接证明
  - 【推断】：根据多处代码推导
  - 【未知】：当前仓库无法确认
- 不得虚构业务规则、调用关系、性能数据或部署方式。
- 对重复模式进行归纳，不要逐文件复述。
- 内容详略得当：主链路深入分析，辅助模块简要说明。

## 二、分析过程

请按以下顺序检查仓库：
1. 阅读 README、项目说明、AGENTS.md、CONTRIBUTING 等约束文档。
2. 查看顶层目录和工作区结构。
3. 阅读依赖、脚本与构建配置。
4. 找出程序入口、请求入口、任务入口或 CLI 入口。
5. 沿入口追踪核心调用链。
6. 检查领域模型、数据访问、外部服务和状态管理。
## 三、输出格式

# 1. 项目速览

用不超过 200 字说明：
- 项目要解决的问题
- 主要用户或调用方
- 核心输入与输出
- 当前项目类型：单体、前后端分离、Monorepo、微服务、库、CLI 或其他
- 一句话架构总结

# 2. 技术栈与运行方式

使用表格：

| 分类   | 技术/组件 | 用途  | 证据  |
| ---- | ----- | --- | --- |
| 语言   |       |     |     |
| 框架   |       |     |     |
| 数据库  |       |     |     |
| 外部服务 |       |     |     |


# 3. 系统架构图

使用 Mermaid `flowchart` 绘制系统全景图

全景图不止一张，可以按照模块组成
1. 顶层抽象模块组成的架构图
2. 模块内部的架构图

不要把所有细节都放在一张图内；
图后解释每个节点的职责。图中不要加入源码无法证明的组件。

# 4. 目录与模块地图

只介绍重要目录：

| 路径 | 职责 | 关键文件 | 依赖对象 | 被谁调用 | 重要度 |
|---|---|---|---|---|---|

重要度使用：

- P0：不理解就无法理解主流程
- P1：重要支撑模块
- P2：辅助工具或非核心功能

不要把目录树原样复制一遍。

# 5. 核心业务链路

分析pipeline业务链路

每条链路必须包含：

1. 触发条件
2. 入口文件与入口函数
3. 按顺序排列的调用过程
4. 数据在每一步如何变化
5. 最终输出
6. 失败路径和降级行为
7. 对应源码证据

为最核心链路绘制 Mermaid `sequenceDiagram`。

# 6. 关键逻辑伪代码

注意：伪代码最好是中文解释写
