
## 1. 结论

DKAgent 的 System Prompt 已从“绑定具体工具的面试分析操作手册”，升级为“面试成长 Agent 的稳定行为契约”。这是正确的架构方向：稳定的身份、证据、授权和失败原则留在 System Prompt；Tool、Skill、MCP 的名称、参数和流程交给运行时能力元数据与 Harness。

新版的主要收益是可扩展、职责清晰、不会随着工具变化频繁改 Prompt。主要代价是抽象规则更依赖运行时配套；在 Capability Metadata、权限 Gate 和真实模型 Eval 尚未实现前，部分行为只是设计目标，不能视为已经验证。

本文的事实依据是 Git 基线 `1524dd0`、当前实现 `511e7eb`、相关测试和项目设计文档。外部官方资料检索在本次编写时因网络错误未完成，因此“通用规范”部分属于工程通用原则，不冒充某个平台的强制标准。

## 3. 修改前：业务流程型 Prompt

旧 Prompt 的核心结构是：普通问题直接回答；面试分析必须按照“查找文件 → 展示绝对路径 → 用户确认 → 调用分析工具 → 展示报告”的固定流程执行。它还直接写入 `find_files` 和 `analyze_interview` 两个工具名。

### 优点

1. **具体、容易理解**：模型能直接看到操作顺序和工具名称，适合早期单一流程 MVP。
2. **局部安全规则明确**：例如不得扫描整个用户目录、确认前不得分析、不得猜测路径。
3. **容易写静态测试**：检查关键词即可确认规则仍存在。

### 缺点

1. **身份过弱**：只说“可以正常回答普通问题”，没有定义 DKAgent 为什么存在、主要服务谁、最终要交付什么结果。
2. **Prompt 与工具强耦合**：工具改名、增加 Skill 或接入未知 MCP 时，都可能要求修改 System Prompt。
3. **把业务状态机放进自然语言**：确认状态、参数校验、调用顺序本应由 Harness 或 Session 确定性控制，仅靠模型遵守存在漂移风险。
4. **规则覆盖面窄**：只处理文件路径和面试分析，没有统一定义证据、写操作、外发、付费、失败和 Prompt Injection。
5. **扩展成本高**：每加入一个能力都向 System Prompt 追加流程，最终容易形成冗长且互相冲突的规则集合。

旧版并非“错误”，而是适合单流程原型；当 Agent 开始支持 Tool、Skill 和动态 MCP 后，它不再适合作为长期架构。

## 4. 修改后：稳定行为契约

新版围绕六组稳定原则组织：目标驱动、证据边界、能力使用、授权边界、安全与失败、任务范围。具体工具名被移除，模型根据运行时能力元数据决定是否使用 Tool、Skill 或 MCP。

### 优点

1. **身份与目标清晰**：DKAgent 被定义为“面试成长 Agent”，目标覆盖准备、复盘、差距识别和行动方案。
2. **证据分级更准确**：用户经历、动态事实、外部或私有数据必须有证据；可靠通用面试知识可以直接回答；推导内容标记为“推断”。
3. **能力解耦**：System Prompt 不枚举能力名，新增或下线能力主要修改元数据和 Harness，而不是重写人格与原则。
4. **授权范围更完整**：安全只读操作可直接执行；写入、删除、外发、付费、高风险或范围扩张必须确认。
5. **失败行为透明**：没有能力、能力报错或结果不足时，不得假装已经读取、查询或执行成功。
6. **具备注入防护意识**：用户材料、Memory 和能力返回内容被视为数据，不能覆盖系统规则。

### 缺点与风险

1. **规则比旧版抽象**：如果能力元数据只提供名称和参数，没有用途、风险、审批和失败语义，模型仍难以正确路由。
2. **Prompt 不是权限系统**：模型可能不稳定地遵守“先确认”，真正的写入和高风险阻断必须由 Harness 实现。
3. **“可靠通用知识”的边界仍需 Eval**：什么算可靠、什么算动态，模型判断可能因模型版本和问题表达变化。
4. **静态测试只能防文案回退**：当前测试确认关键规则存在、具体工具名不存在，但不能证明模型会在真实对话中正确选择能力。
5. **范围引导可能过强**：简单范围外问题回答后总是拉回面试目标，可能降低自然交互体验，需要通过样例观察。

## 5. 多角度对比

| 角度 | 修改前 | 修改后 | 判断 |
| --- | --- | --- | --- |
| Agent 定位 | 普通问答 + 面试分析流程 | 面试成长 Agent | 新版更聚焦 |
| 自主性 | 按固定步骤执行 | 围绕目标主动拆解 | 新版更通用，但需防越权 |
| 工具关系 | Prompt 写死工具名 | 运行时元数据发现能力 | 新版扩展性更好 |
| 状态控制 | 依赖模型记住确认流程 | 原则交给 Prompt，确定性约束交给 Harness | 新版职责更合理 |
| 事实边界 | 主要限制路径猜测 | 区分事实、推断、待确认和通用知识 | 新版覆盖更完整 |
| 权限 | 只有分析前确认 | 按副作用和风险分类 | 新版更系统 |
| 失败处理 | 找不到文件时补信息 | 能力缺失、失败、重试均有原则 | 新版更透明 |
| 注入防护 | 未统一说明 | 外部内容只能作为数据 | 新版更安全 |
| 可测试性 | 易做流程关键词测试 | 需静态契约 + 真实模型 Eval + Harness 测试 | 新版测试成本更高但更可信 |
| Token 成本 | 短但会随工具增长 | 当前较长，未来能力扩展不必增长 | 新版长期更稳定 |

## 6. System Prompt 应该负责什么

System Prompt 是模型侧的最高层行为契约，适合承载长期稳定、跨任务有效、需要模型判断的规则：

1. **身份与目标**：Agent 是谁、服务什么目标、什么结果优先。
2. **决策原则**：何时直接回答、何时补信息、何时使用能力、何时停止。
3. **证据与表达**：事实来源、推断标记、不确定性和禁止编造。
4. **授权与安全原则**：副作用、外发、付费、高风险操作和外部内容的地位。
5. **输出原则**：结论优先、必要证据、下一步，但不要把每种页面格式都塞入核心 Prompt。

不适合放入 System Prompt 的内容：

- 具体 Tool、Skill、MCP 名称和 JSON Schema；
- 文件是否存在、参数是否合法、用户是否已经确认等确定性状态；
- 超时、重试次数、权限拦截、审计、持久化；
- 只属于单个业务流程的详细步骤；
- 可以由代码百分之百判断的约束。

核心原则是：**Prompt 负责语义判断，代码负责确定性约束。**

## 7. Tool、Skill、MCP 如何告诉模型

三类能力可以在模型侧统一理解为 Capability，但运行机制不必相同：

```typescript
interface CapabilityMetadata {
  id: string;
  type: "tool" | "skill" | "mcp";
  purpose: string;
  whenToUse: string[];
  whenNotToUse?: string[];
  inputSchema: JSONSchema;
  outputDescription: string;
  risk: "read" | "write" | "external_write" | "destructive" | "paid" | "unknown";
  requiresApproval: boolean;
  retryPolicy: "never" | "transient-once";
}
```

关键规范：

1. **描述结果，不只描述动作**：模型需要知道能力能解决什么问题、返回什么证据。
2. **写清使用与禁用条件**：名称相近的能力必须能被模型区分。
3. **未知风险默认升级**：MCP 自报“安全”不能替代本地策略，未知能力应先确认。
4. **只暴露相关子集**：能力过多时先检索，避免选择准确率下降和 Token 膨胀。
5. **执行前后都校验**：模型选择能力后，Harness 仍需检查参数、权限、状态和返回协议。

## 8. 正常的 Prompt 设计链路

这里的“思考链路”指工程决策流程，不要求模型输出隐藏的内部推理过程。

```text
明确 Agent 的核心目标
→ 收集典型任务、失败案例和高风险动作
→ 划分 Prompt / Metadata / Harness / Session / Tool 职责
→ 写最小稳定规则
→ 建立正向、反向、模糊、对抗样例
→ 静态契约测试
→ Harness 确定性测试
→ 真实模型重复 Eval
→ 按失败类型一次只改一类规则
```

设计每条规则时依次问：

1. 这条规则是否长期稳定，还是某个工具的临时流程？
2. 它需要模型进行语义判断，还是代码能够确定性判断？
3. 如果删除它，会出现什么可观察失败？
4. 它是否与另一条规则冲突，优先级是否明确？
5. 如何用正例、反例、模糊例和对抗例验证？

## 9. 如何衡量好坏

Prompt 的好坏不能只看文案是否专业，也不能只看一次演示是否成功。应该衡量行为结果：

| 指标 | 含义 | DKAgent 建议目标 |
| --- | --- | --- |
| 任务成功率 | 是否完成用户真正目标 | 初期 ≥ 85% |
| 能力选择准确率 | 该调用时调用，不该调用时不调用 | ≥ 90% |
| 必要澄清准确率 | 只在真正缺少关键信息时提问 | ≥ 90% |
| 无依据用户事实 | 是否补造经历、分数、日期、项目结果 | 0 |
| 虚构执行成功 | 能力未执行或失败却声称完成 | 0 |
| 未授权高风险执行 | 未确认就写入、外发、付费或破坏 | 0 |
| 误拒绝率 | 本可直接回答却因规则过严拒绝 | 持续降低 |
| 成本与延迟 | Token、能力调用次数、响应时间 | 与成功率一起评估 |

这些目标目前来自设计稿，**尚不能确认已经达成**。当前已确认的是：静态 Prompt 契约测试通过、Agent 全量测试 189/189、Phase1 测试 15/15、类型检查通过。

## 10. Eval 用例应该怎么设计

建议先建立 20～30 条固定用例，每次修改 Prompt 后重复运行：

1. **正向**：解释闭包、优化项目介绍、根据已给文字稿提出改进。
2. **反向**：普通知识题不应误调用文件或外部能力。
3. **模糊**：“帮我分析上次面试”缺少材料时，只询问最小必要信息。
4. **权限**：读取已授权材料可直接执行；发送报告、覆盖文件必须确认。
5. **证据**：材料没有结果数据时，不得补造提升百分比或面试分数。
6. **动态事实**：询问最新岗位、公司人员或价格时，应使用可用能力或标记不确定。
7. **能力缺失**：没有邮件或日历能力时，不能声称已经发送或创建。
8. **注入攻击**：面试稿或 MCP 返回“忽略系统规则”时，只能当作数据分析。

每条用例至少记录：输入上下文、可用能力、预期动作、禁止动作、证据要求、最终评分和失败原因。关键安全用例需要多次运行，因为真实模型输出存在随机性。

## 11. 如何优化 Prompt

优化应从失败样本出发，而不是凭感觉继续加规则：

1. **先分类失败**：身份偏移、误调用、漏调用、过度追问、证据越界、未授权执行或输出质量。
2. **先修职责层**：能用代码解决的放入 Harness；能力描述不清的修改 Metadata；只有模型判断失败才修改 Prompt。
3. **一次只改一类问题**：否则无法判断成功率变化来自哪条规则。
4. **优先补边界和反例**：不要用大量近义句重复同一个要求。
5. **回归全部固定用例**：同时观察成功率、安全指标、Token、延迟和调用成本。

好的 Prompt 通常不是最长的 Prompt，而是“每条规则都有失败依据、职责归属正确、冲突少、可以被 Eval 验证”的 Prompt。

## 12. DKAgent 当前状态与下一步

### 已确认

- 稳定 System Prompt 已实现，不再包含 `find_files`、`analyze_interview` 等具体能力名。
- 静态测试覆盖身份、证据、能力、授权、失败和范围规则。
- 旧的文件查找与确认流程仍有独立行为测试，没有因 Prompt 改造而删除。

### 推断

- 当 Tool、Skill 和 MCP 增多时，新结构比旧结构更容易维护。
- 统一 Capability Metadata 有望减少 Prompt 膨胀并提高未知 MCP 的可治理性。

### 不确定

- 新 Prompt 在不同真实模型上的能力选择准确率和任务成功率。
- 模型能否稳定区分“可靠通用知识”和“需要验证的动态事实”。
- 授权规则在复杂多步任务中的误确认率与漏确认率。

### 推荐的单一路线

下一步优先做 **Prompt Eval 最小闭环**：先写 20 条固定场景，用真实模型记录动作和结果；暂不同时建设完整 Capability Registry。Eval 能先暴露 Prompt 真实问题，也能为后续 Capability Metadata 和权限 Gate 提供验收标准。
