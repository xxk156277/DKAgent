
## 一、先明确：RAG 评估分两层，你现在只需要第一层

生产前评估最常见的误区是"一上来就测最终答案好不好"。但你的 `search` 现在**只做检索、不生成答案**，所以要先分层：

```
第 1 层：检索评估（你当前阶段）—— 找得对不对
第 2 层：生成评估（接 DeepSeek 之后）—— 答得对不对
第 3 层：端到端评估（整体）—— 用户满意吗
```

| 层 | 核心问题 | 核心指标 |
|---|---|---|
| **检索** | 正确的文档进 Top-K 了吗？ | **Recall@K** |
| **生成** | 答案忠实于检索内容吗？答非所问吗？ | Faithfulness、Answer Relevance |
| **端到端** | 真实用户体验 | 人工评分、A/B |

**你现在只做第一层：Recall@3。** 这正是你笔记里一直在提的指标。生成阶段的指标（RAGAS 那些）等接上 DeepSeek 再说。


## 二、评估集（20 题）怎么设计

这是最关键的资产，比代码还重要。你笔记里说的"20 题"就是一个 **黄金评估集（Golden Set）**。

### 1. 题目从哪来

**从真实使用场景反推，而不是随便编。** 你是"面经 RAG"，那题目就应该是你未来真的会问的问题。比如：

```
✅ "SSE 和 WebSocket 的区别是什么？"
✅ "React Fiber 解决了什么问题？"
✅ "浏览器缓存有哪几种？"
❌ "把 SSE 那篇文档的内容复述一遍"（这种不是真实问题）
```

### 2. 每题必须标注"正确答案"（Ground Truth）

这是最难也最不能省的一步。每题标注：**这个问题，答案应该来自哪几篇父文档。**

```
题1：SSE 和 WebSocket 的区别
  ground_truth: ["C-前端学习/node/SSE.md", "C-前端学习/node/websocket.md"]

题2：React Fiber 是什么
  ground_truth: [".../React原理/3. Fiber架构.md"]
```

> ⚠️ 这个标注必须**人工做**，而且要基于"你期望系统返回什么"，而不是"系统现在返回什么"——否则评估就失去意义了。

### 3. 20 题要覆盖不同难度类型

你笔记第 13 节的归因表已经暗示了分类。建议这样配比：

| 类型 | 占比 | 目的 |
|---|---|---|
| **简单直接**（术语解释、单文档） | 8 题 | 验证基线能力 |
| **跨文档**（需要多个来源） | 4 题 | 验证召回充分性 |
| **易混淆**（SSE vs WebSocket 这类） | 4 题 | 暴露 Dense 语义泛化问题 |
| **拒答类**（知识库没有的） | 4 题 | 验证是否该返回"无相关" |

你第 12 节发现的"SSE 混淆 WebSocket"问题，就应该**专门设计成易混淆类题目**放进去，看它是不是普遍失败。


## 三、Recall@3 怎么算

对每一题，跑检索，看 **ground_truth 里的文档有没有出现在返回的 Top-3 里**：

```
题1：SSE 和 WebSocket 的区别
  ground_truth: [SSE.md, websocket.md]
  系统返回 Top-3: [SSE.md, websocket.md, 其他.md]
  → 命中 2/2 篇，本题算"对"

Recall@3 = 20 题中"对"的题数 / 20
```

如果标准严格一点，可以算 **"至少命中一篇 ground truth 就算对"**，或者 **"ground truth 全部命中才算对"**。第一版建议用前者（宽松），先把基线建立起来。

### 落地建议

- 写一个 `eval.ts` 脚本，读 20 题的 JSON，循环调 `search`，自动比对，输出表格
- 评估集存成文件（如 `eval/golden-set.json`），**不要散在代码里**
- 每题记录：query、ground_truth、实际 Top-3、命中与否


## 四、评估结果怎么看：不是"一个分数"，而是"归因清单"

你笔记第 13 节的表格已经是正确思路了。评估产出的核心价值是这张表：

| 现象 | 归因方向 | 下一步 |
|---|---|---|
| 正确文档完全没进候选 | Embedding/切块/术语差异 | 查数据和切块 |
| 正确子块在 Top-12 但父文档没进 Top-3 | 聚合问题 | 调聚合逻辑 |
| 易混淆题大量失败 | Dense 语义过度泛化 | **这才考虑 BM25 + RRF** |
| 拒答类也返回高分文档 | 缺相似度阈值 | 加阈值/拒答逻辑 |

**关键判断标准**：某个失败类型如果只是 1-2 题，可能是个例；如果是同一类型反复失败（比如 4 道易混淆题全错），才是系统性问题，才值得引入新机制（BM25/RRF/重排）。

这正是你选中那句话的精髓：**先量化"是否重复失败"，再决定加不加复杂度。**


## 五、评估集的两个铁律

1. **冻结评估集**：评估集一旦定好就不要再改。如果边调边改答案，你就会"调参调到过拟合自己那 20 题"，上线照样翻车。
2. **评估要可重复**：每次改代码都能一键重跑 20 题，得到新分数和旧分数对比。这是你的**回归护栏**——以后加任何功能（BM25、重排、改切块），先跑评估确认没变差。


## 六、后续（接生成后）再补第二层指标

等你接上 DeepSeek 生成答案后，再补：

| 指标 | 测什么 |
|---|---|
| **Faithfulness（忠实度）** | 答案是不是基于检索到的内容，有没有瞎编 |
| **Answer Relevance** | 答案是否直接回答了问题 |
| **Context Precision** | 检索结果里相关文档的排位质量 |

这些用 RAGAS 等框架能半自动化算，但你笔记 [[0.RAG介绍]] 第 5 节列过，当前阶段不用碰。


## 一句话总结

**生产前 RAG 评估的正确姿势：先用 20 题黄金集测检索层（Recall@3），把失败按类型归因，只有"同类型反复失败"才引入新机制；评估集要冻结、可重复，成为后续所有改动的回归护栏。**
