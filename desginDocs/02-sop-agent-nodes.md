# 面试分析 SOP、Agent节点与Skill编排

## 1. 控制边界

```text
用户 ↔ Agent → diagnose-transcript Skill → Tool → LLM或基础设施
```

| 层级 | 职责 | 不负责 |
|---|---|---|
| Agent | 理解用户意图、收集元数据/JD、提出事实确认、理解补充、交付报告 | 不控制逐题顺序，不计算总分，不直接写时间线 |
| Skill | 控制固定SOP、逐题循环、暂停恢复、失败降级和完成条件 | 不自由改变业务目标，不猜测用户事实 |
| Tool | 接收明确Schema，完成一个可复用业务能力 | 不决定下一步调用哪个Tool |
| LLM | 在指定输入、Rubric和输出Schema内完成语义判断 | 不修改原稿，不直接算总分或写长期记忆 |
| 基础设施 | Context、Session、Memory、知识库和文件存储 | 不进行面试语义判断 |

V1不新增Workflow Engine。业务流程是文档层面的Workflow，运行时由Skill控制，暂停恢复由Session保存。

## 2. Agent控制的节点

Agent只控制与用户交互有关的节点：

1. 识别“分析面试”意图，获取用户提供的原始文件路径。
2. 从文件名和文字稿提取公司、岗位、日期、轮次，请用户确认。
3. 询问用户是否提供JD；未提供时继续通用分析。
4. 启动 `diagnose-transcript` Skill。
5. 初步分析后展示3～5个关键疑点，接收用户补充。
6. 根据Session中的活动诊断任务恢复Skill。
7. 交付最终报告并回答用户后续问题。

Agent不得自行跳过题目、改变权重、提前写Memory或把推断当成用户确认事实。

## 3. Tool清单

| Tool | 输入 | 输出 | 实现方式 |
|---|---|---|---|
| `read_file` | `filePath` | 原始文字、文件信息 | 代码，复用现有Tool |
| `preprocess_transcript` | 原始文字 | 分析稿、错词Diff、原文映射 | 代码预处理＋LLM纠错 |
| `split_qa_pairs` | 分析稿、原文映射 | 问题簇、全部具体问题、回答、题型 | LLM结构化判断 |
| `extract_project_facts` | 问题簇、完整文字稿 | 项目事实、个人边界、指标、疑点 | LLM结构化提取 |
| `analyze_expression` | 原回答、表达标记 | 统计结果、影响判断 | 代码统计＋LLM判断 |
| `query_knowledge_base` | 问题、检索范围 | 带来源的参考资料 | FTS5／Embedding检索 |
| `analyze_answer` | 问题、回答、题型、项目事实、参考资料 | 单题分析、维度分、证据、置信度、待确认项 | LLM按题型Rubric分析 |
| `generate_report` | 全部诊断、历史趋势、可选JD | 两层最终报告 | 代码算分＋LLM总结＋模板渲染 |

Tool是能力接口，LLM是部分Tool的实现依赖。Skill决定何时调用Tool，LLM不能自由编排下一步。

## 4. diagnose-transcript Skill SOP

### 阶段A：任务建立

1. 校验文件路径、面试元数据和用户确认结果。
2. 调用 `read_file` 获取原始文字稿。
3. Session记录任务ID、原稿引用、元数据和阶段 `preparing`。

### 阶段B：文字稿结构化

1. 调用 `preprocess_transcript` 生成分析稿和错词Diff。
2. 调用 `split_qa_pairs` 形成问题簇和全部具体问题。
3. 校验每个问题和回答都能定位到原文。
4. 调用 `extract_project_facts` 建立本场项目事实表。
5. 调用 `analyze_expression` 生成全场及逐题表达指标。
6. 保存检查点，阶段更新为 `structured`。

### 阶段C：逐题分析

Skill按问题簇顺序遍历全部具体问题：

1. 过程性问题保留，但标记为不参与评分。
2. 八股题或需要技术核验时调用 `query_knowledge_base`。
3. 调用 `analyze_answer`，使用对应题型Rubric。
4. 保存单题诊断、原文证据、维度分和置信度。
5. 单题失败时标记失败并继续，不丢弃已完成结果。

每次模型请求只加载当前问题簇、相关项目事实、必要参考资料和历史摘要，不加载整场全部诊断结果。

### 阶段D：初步分析与暂停

1. 汇总所有单题待确认项。
2. 选择3～5个会显著影响评分或结论的问题。
3. 保存初步诊断，Session阶段更新为 `awaiting_confirmation`。
4. 将确认问题返回Agent，由Agent与用户对话。

此阶段不生成最终报告、不写入长期Memory。

### 阶段E：确认与最终报告

1. Agent将用户补充传回Skill。
2. Skill更新项目事实，只重跑受影响的 `analyze_answer`。
3. 调用 `generate_report`，按固定权重生成总分和两层报告。
4. 报告成功后，Session阶段更新为 `completed`。
5. 将本次表现摘要写入Memory时间线。

## 5. 题型分析规则

| 题型 | `analyze_answer`使用的重点 |
|---|---|
| 项目题 | 本人贡献、决策依据、实施细节、指标证据、追问一致性 |
| 八股题 | 事实正确性、关键点、原理深度、知识库证据 |
| 开放题 | 澄清、约束、拆解、权衡、风险、验证 |
| 行为题 | 情境、行动、协作、结果、复盘 |
| 手写题 | 思路、代码产出、样例、边界、复杂度 |

不同题型输出统一为全局五维分数，缺少证据的维度降低置信度，不补造事实。

## 6. 报告数据结构

第一层保存：

- 元数据、材料边界、总分和水平说明。
- 五维分数、核心强项、核心问题。
- 可选JD匹配、历史趋势、三项优先改进。

第二层每条问题保存：

```text
原问题
原回答
标签：所属问题簇与题型
问题
改进方向
分数与置信度
```

连续追问分别展示，所属问题簇负责汇总评分。过程性问题展示但不评分。

## 7. 错误与恢复

- 文件不存在、角色不可识别或内容过短：停止任务，不生成报告。
- 拆题置信度过低：暂停并请求用户确认缺失片段。
- 知识库失败：继续分析，但技术正确性降低置信度。
- 单题LLM失败：记录失败并继续，其余结果保留。
- 用户未确认：保持 `awaiting_confirmation`，不写长期Memory。
- 报告生成失败：保留全部诊断，可重试生成。
- Memory写入失败：报告仍然成功，记录错误并允许重试。

## 8. 测试与验收

- Tool单测：文字稿预处理、表达统计、固定权重算分、文件与数据库错误。
- Prompt评测：项目题、八股题、开放题、行为题、手写题及证据不足案例。
- Skill集成测试：完整SOP、单题失败、知识库降级、暂停恢复、局部重跑。
- Memory测试：最终报告前不写入，完成后新增时间线且不覆盖旧记录。
- 人工验收：使用脱敏长稿和真实字节面试稿检查问题覆盖、问题簇、证据和报告可读性。
